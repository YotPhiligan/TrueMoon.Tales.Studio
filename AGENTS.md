# Работа над TrueMoon Tales Studio

Назначение: приложение видеопродакшена, локальный API/CLI, UI, тесты и общая
интеграция ComfyUI. [README](README.md), [общие инструкции](../Guidelines.md).
[Карта проектов](../Projects.md).

Перед задачей в общей рабочей области явно прочитать общие документы TrueMoon.Tales по ссылкам
выше, затем применимые правила этого файла и вложенных AGENTS.md. Наличие ссылки
не означает, что её содержимое уже прочитано. Если открыт отдельный клон/worktree,
найти зонтик TrueMoon.Tales в подтверждённой основной рабочей области; пути к материалам не угадывать.
При автономной разработке публичного клона Studio без зонтика TrueMoon.Tales следовать
локальным правилам этого файла; доступ к материалам и лору подключать только по
подтверждённым внешним путям. Отсутствие частных материалов не мешает самодостаточной
технической задаче, которой они не нужны.

В этом репозитории находится активный код Studio 0.15 после M2. Перед технической
задачей читать [README](README.md), [Workspace](Workspace.md),
[Architecture](Architecture.md), [модель проекта](ProjectModel.md), [Plan](Plan.md), [Status](Status.md), API и нужный проверочный отчёт.
Старая UI 0.14 в Book сохранена как исходный архив; новые правки кода выполняются
только здесь. Проекты Клэр/опенинга перенесены в Videos в M4.

Соседний `TrueMoon` развивается параллельно: в миграционных задачах не перемещать,
не копировать, не исправлять и не восстанавливать его файлы. Проверять Git только
чтением с `--no-optional-locks`; изменения другой работы не считать поломкой.
Studio исключает этот каталог из доступа через resolver.

- Сохранять разделение кода и пользовательских данных: проекты — Videos,
  общие референсы — Arts, тексты/лор — внешние источники, runtime state/cache отдельно.
- При поддержке внешних корней сохранять allowlist путей, ограничение записи,
  expected_revision, атомарное сохранение, историю и защиту конфликтного черновика.
- Перенос сохраняет существующие ID/связи/тайминги и immutable снимки. Не менять
  авторские проекты/генерации, чтобы упростить тест или получить чистый Git.
- Подготовка workflow не отправляет очередь; чтение/запуск UI не запускают GPU.
  Prepare/launch/collect, таймеры/watchdog, проверка владения процессами и
  восстановление без повторной отправки сохраняются.
- Изменения preview/монтажа проверять с учётом соответствия CPU MP4: участки,
  скорости, звук, переходы, кириллица/титры. Использовать отдельный тестовый проект.
- GPU, длительные/аппаратные проверки и установка моделей требуют соответствующего
  запроса; не занимать чужие порты/очереди и не закрывать пользовательские процессы.
- Тесты/синтаксис/ссылки выбирать по изменению. Старые отчёты описывают прошлую
  конфигурацию, а не доказывают работоспособность после переноса.
- После завершения этапа обновлять Status.md с результатом и границами проверки. План и критерии вести в Plan.md.
- Код остаётся Python/JS до отдельного
  технического решения; наличие C# фреймворка не является миграцией реализации.

## Модель проекта: действия, источники и монтаж

Нормативная целевая модель — [ProjectModel.md](ProjectModel.md), согласована
09.11.2026. Читать её перед изменением сценария, библиотеки, монтажа или их контрактов.

- Сценарий состоит из сегментов и блоков-действий. Действие может включать один
  план или несколько склеек, ссылаться на несколько источников и реализовываться
  несколькими клипами. Пустой список источников допустим на этапе замысла.
- Источник — библиотечная сущность с постановкой/импортом и дублями; один источник
  может использоваться несколькими действиями. Назначение материала хранить
  в связи с действием, выбранный дубль и участок — в монтажном использовании.
- Монтажное окно ссылается на тот же смысловой сегмент. Группы клипов действия
  представляют общий монтаж. Плановое время, длину материала и фактическую
  монтажную длительность различать; фиксированное окно сегмента сохраняется.
- Целевой split сохраняет действие при создании нескольких клипов. Текущая
  реализация ещё использует связь сценарного использования и клипа 1:1.
  Не выдавать новое описание за реализованную схему; поля `blocks`/`block_id`
  и существующие API-команды менять только через явный контракт совместимости.
- В миграции сохранять ID, связи, тайминги, историю и immutable снимки. Чтение
  проекта не запускает преобразование. Критерии реализации вести в Plan.md.

## M4 · Book отключён

Видео/Production/исследования находятся в TrueMoon.Tales.Videos. Конфигурация
`legacy_read_enabled: false` оставляет legacy_root только логическим пространством
старых имён: стат/чтение/запись туда запрещены, unmapped пути возвращают 403.
Aliases перенаправляют относительные и абсолютные старые строки до файлового IO.
Экспорт получает только реальные новые пути. Исторический prepared с config в старом
пространстве имён возвращает 409 без запуска/мутации; подготовить свежий дубль.
Новые prepare/launch работают с новыми физическими путями. Исторические снимки
не переписываются. Для применения конфигурации перезапустить Studio.

## Ограничения TrueMoon и заявки владельцам модулей

Перед разработкой инфраструктурной возможности в Studio проверять, как её
можно собрать на API используемых пакетов TrueMoon. Переиспользовать готовые
контракты для конфигурации, UI, процессов и IPC, если они покрывают сценарий.
При появлении общего решения в Studio оценивать его пользу для других приложений.
Поведение предметной области видеопродакшена принадлежит Studio. Если общий
контракт или улучшение полезны другим потребителям, описывать конкретные сценарии
и критерии во входящем контуре заявок TrueMoon. После выпуска пакета сверить
сквозной сценарий Studio и убрать заменённый локальный код.

При обнаружении ограничения/недостающей возможности сначала сверить API текущего
пакета, исходники, план модуля и существующие запросы. Подтверждённую потребность
фиксировать отдельной заявкой в `.local/requests/<module>/` основного checkout
общей рабочей области. Сначала прочитать `.local/requests/README.md`. Указать
пример, критерии готовности и влияние на задачу Studio в локальной карточке.
В публичных Plan/Status Studio оставлять техническую задачу и проверяемый
результат, пригодные для публикации. Непроверенный сценарий не объявлять
дефектом, существующую задачу не дублировать.

Автор сохраняет Request/Notes в общей локальной очереди, владелец модуля
принимает заявку через эксклюзивный Claim и Decision и ведёт реализацию
в своём PLAN. Общие планы и чужие незакоммиченные изменения сохранять,
перед записью сверять актуальный SHA. Заявка передаёт потребность владельцу
модуля, у которого остаётся право менять код и очередь фреймворка.

## Проверки UI на TrueMoon

Перед изменением UI читать [инструкцию Studio](src/UITesting.md) и доступное
[общее руководство Alloy/Argentis](../TrueMoon/src/docs/alloy/UI_TESTING.md).
По умолчанию выбирать UiSession/routed input и CPU raster по проверяемому контракту;
Computer Use не является обязательным условием UI-тестов. Различать fake metrics,

Для отдельного клона минимальные правила и сценарии сохраняются в src/UITesting.md.

## Жизненный цикл проверочных процессов

Проверочные Python-серверы, native UI и вспомогательные процессы не оставлять
после задачи. Для изолированных проверок окна использовать управляемый запуск
`src/Verification/WindowMenusQA.py --ui <exe>` по [инструкции QA](src/QASessions.md).
Не запускать QA-сервер через прямой `app.py` и окно отдельным бесконтрольным
`Start-Process`: оба процесса должны принадлежать одной ограниченной сессии.

До запуска сверить `--status`, сохранить ID новых сессий и tool session IDs.
У запуска должны быть дедлайн, журнал и владелец; очистка — в `finally`, включая
ошибку старта, отмену и таймаут. Перед финальным ответом остановить свои сессии
через `--stop <id>`, дождаться завершения tool sessions и проверить отсутствие
принадлежащих задаче процессов. Для новых QA-сессий Windows Job Object завершает
всех потомков и при аварии контроллера; время жизни по умолчанию 15 минут.

Не считать номер PID доказательством владения: сверять exe, команду и время
создания, а при остановке исключать повторное использование PID. Старые запуски
вне registry проверять отдельно. Не завершать все `python`/`ffmpeg` по имени,
пользовательские приложения, ComfyUI и сессии другого агента. `--stop-all`
применять только при явном запросе на общую остановку. Оставлять окно/сервер
после задачи можно только по явному запросу пользователя с указанием ID и срока.

## Версионирование поставок

Принято 15.11.2026. Формат версии продукта/пакетов —
`x.yyMM.d.rev[-postfix]`, например `1.2611.15.1-alpha`.

- `x` — поколение продукта/API; менять только по явному решению владельца.
  При первом переходе со старой схемы использовать `1`, сохраняя стадию `alpha`.
- `yyMM` и `d` — год/месяц и день по **UTC**; день записывать без ведущего нуля.
- `rev` — общий для всех postfix счётчик поставок данного репозитория за эту
  дату: первая — `1`, следующая — `2`; при новой дате начинать с `1`.
- Postfix — `alpha`, `beta` или `rc`; отсутствие postfix означает стабильную
  поставку. Стадию менять только по явному решению, не выводить её из passing
  тестов. Смена стадии не сбрасывает `rev`.

Пример последовательности: `1.2611.15.1-alpha` → `1.2611.15.2-alpha` →
`1.2611.16.1-alpha` → `1.2611.16.2-beta` → `1.2611.16.3-rc` → `1.2611.16.4`.

После завершённого набора изменений production-кода, генераторов, зависимостей,
native-библиотек, шейдеров, поставляемых ресурсов либо влияющих на артефакты
build/pack/publish правил агент обязан обновить общую `Version` в указанном ниже
`Directory.Build.props`. Один набор изменений — одно повышение версии, а не
повышение на каждый файл, промежуточную правку, тест или коммит внутри задачи.
Только документация/планы/инструкции либо только тесты не требуют повышения;
повторная поставка с изменённым содержимым пакета/дистрибутива требует новой версии.

Версию и дату зафиксировать **до финальной сборки, проверок и упаковки** и
использовать согласованно во всех артефактах и evidence этой поставки. Повторная
сборка тех же зафиксированных входов, в том числе после полуночи UTC, сохраняет
версию. Изменённое содержимое уже опубликованной поставки получает новую версию;
существующие пакеты/immutable manifests не перезаписывать. Промежуточные локальные
QA-версии через `-p:Version` не заменяют обновление общей версии в репозитории.

Перед выбором номера сверить текущую версию рабочей копии и актуальной целевой
`main`; перед слиянием повторить сверку. Версия нового production-набора должна
быть выше обеих по правилам сравнения NuGet, а не по строковому сравнению или
только относительно старого merge-base. При совпадении номеров параллельных веток
координатор выбирает следующий `rev` и повторяет затронутую финальную проверку
на итоговой версии. Общую версию меняет один координатор задачи; участники
параллельной работы не повышают её независимо друг от друга.

Все собственные проекты одной поставки используют общую версию своего
репозитория. TrueMoon, Studio и игра ведут независимые счётчики; одинаковая схема
не требует одинаковых номеров и не обновляет автоматически версии зависимостей.
Сохранять существующие условия/переопределения `Version`; не добавлять повышение
номера на каждый запуск MSBuild. Версии ABI, протоколов, форматов документов,
ассетов и сторонних библиотек меняются по собственным правилам совместимости.
Не вводить отдельную политику AssemblyVersion/FileVersion только ради этой схемы.
Исторические версии, manifests и результаты проверок не переписывать.

Эта документационная фиксация не меняет текущую `Version`; первый следующий
production-набор обязан перейти на принятую схему до финальной проверки.

Источник версии Studio — [src/Directory.Build.props](src/Directory.Build.props).
Правило охватывает C#, Python/JS и поставляемые ресурсы Studio. При переходе
legacy Python/JS-поставки согласовать продуктовые метки запуска/health с общей
версией; версии HTTP/IPC-контрактов менять только по правилам их совместимости.
`StudioTrueMoonVersion` в `src/Directory.Packages.props` задаёт зависимость от
TrueMoon и не является версией Studio. Старые обозначения 0.15 в исторических
описаниях и отчётах сохранять; этот документационный этап не меняет runtime-метки.
